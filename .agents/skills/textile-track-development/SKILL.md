# Textile Track Development

Use this workflow to keep changes consistent across the React frontend, FastAPI API, and SQLModel database layer.

## Establish the current contract

Read the repository-root `AI_README.md` before changing code. Treat it as the source of truth for architecture, commands, routes, database rules, and the completion checklist. If this skill conflicts with `AI_README.md`, follow `AI_README.md` and update the stale skill in the same change. Inspect the implementation and tests related to the requested change rather than relying on an older description of the project.

When the user requests a review, inspect and report prioritized findings without editing files unless the user also asks for fixes. For implementation tasks, classify the change before editing:

- Frontend behavior or UI
- Backend route or business logic
- Shared API request or response contract
- SQLModel schema or database behavior
- Tooling, configuration, or documentation

A change may belong to more than one category. Follow every applicable section below.

## Frontend changes

- Build forms and controls from the local shadcn/ui primitives. Keep reusable primitives generic and application composition outside `components/ui`.
- Follow the existing responsive Tailwind patterns and keep user flows usable at 320px width. Full-page entry screens use the established `min-h-svh` approach.
- Preserve semantic HTML, associated form labels, keyboard navigation, visible focus, and usable loading, error, and empty states.
- Keep workspace navigation and role visibility in `frontend/src/config/workspace-navigation.ts`; do not create separate sidebar definitions per role.
- Keep HTTP calls and their TypeScript contracts in `frontend/src/api.ts`. Do not add raw component-level fetch calls or hardcoded backend origins.
- Keep workspace routes inside `RequireAuth`; only administrators open `/admin/*`.
- Add or update Vitest and Testing Library coverage for user-visible behavior.

## API and contract changes

- Keep public endpoints under `/api` and Swagger at `/docs`.
- Describe request and response bodies with Pydantic models in `backend/app/schemas.py` rather than exposing persistence models as the API contract by accident.
- Keep create, update, and read schemas separate when their fields differ. Never expose password hashes, secrets, internal authorization state, or unrestricted persistence fields in responses.
- When an API contract changes, update the route, Pydantic schema, `frontend/src/api.ts` types and request helper, and relevant backend and frontend tests together.
- Use async route handlers unless a synchronous dependency or operation makes a synchronous handler appropriate. Follow the established dependency-injection pattern rather than opening unmanaged resources in routes.
- Treat the role derived from the frontend URL as presentation-only. Never authorize a request from a client-supplied role or unrestricted `site_id`; when authentication exists, enforce identity, role, and site membership in the backend.
- Cover new routes and important error behavior with backend tests.

## SQLModel and MySQL changes

- SQLModel is the repository ORM. Define persistent table models and database enums in `backend/app/models.py`; do not introduce a second ORM or a parallel model location.
- Use the engine and yielded `Session` dependency from `backend/app/database.py`. Keep credentials in the root `.env` or `DATABASE_URL`, construct URLs without unsafe interpolation, and never log secrets.
- Use the existing MySQL service in `compose.yaml` for local persistent development. Do not silently replace it with SQLite for application behavior; SQLite is acceptable for isolated tests where the existing suite uses it intentionally.
- Alembic is the only supported mechanism for creating or evolving persistent schema. Never add `SQLModel.metadata.create_all()` to application startup or production code. It may be used in isolated tests that create disposable databases.
- A model change that alters persistent metadata requires a reviewed Alembic revision. Do not create empty revisions for Python-only behavior changes. Inspect autogenerated operations, constraint names, enum representation, foreign-key deletion behavior, upgrade behavior, and downgrade behavior instead of accepting autogeneration blindly.
- Never rewrite a migration that may already be applied or shared; add a new revision. Destructive or lossy operations require an explicit data migration, compatibility and rollback plan, and user authorization for the data impact.
- Apply committed migrations to an upgraded database and run `npm run db:check` before declaring a model change complete. If MySQL is unavailable, report the unperformed checks explicitly; do not claim migration compatibility from SQLite-only tests.
- Preserve the named MySQL volume. Never run `docker compose down -v` or otherwise reset stored data unless the user explicitly requests a database reset.
- If a local database references revisions absent from the current branch, do not edit the revision table or reset the volume. Validate with a fresh disposable database or CI and report the branch/database mismatch.
- Preserve domain invariants documented in `AI_README.md`: site-scoped access, exactly one site membership for Staff, immutable submitted EPR snapshots, and append-only dated EPR adjustments. Enforce invariants in write paths when database constraints alone cannot express them.
- Keep multi-row state transitions atomic. Roll back failed writes and consider concurrency, idempotency, and row locking for sorting, handoff, import, and EPR submission flows.

## Verification

Run commands from the repository root and activate `.venv` before direct Python commands. Always run `npm run guardrails` and `npm run format:check`. Select the remaining checks based on the affected surfaces:

- Frontend-only: frontend tests, frontend lint, and `npm run build`.
- Backend behavior: focused Pytest coverage and Ruff checks.
- Shared API contract: backend tests, frontend tests and lint, and `npm run build`.
- SQLModel or migration: `npm run db:migrate`, `npm run db:check`, `npm run test:backend`, and `npm run lint` against upgraded MySQL.
- Tooling or configuration: validate the changed configuration and update `README.md` plus `AI_README.md` when commands, architecture, ports, routes, or environment variables change.

Before finishing, review the diff for unrelated edits, generated files, secrets, missing contract updates, and missing documentation. Report what changed, what was verified, and any checks that could not be run. Do not bypass Husky or commit-message hooks; `npm run commit` and CI both run the executable project guardrails, and commits use the repository's Gitmoji format.
